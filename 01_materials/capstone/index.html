Mental model · 02 / 15

Model + harness = agent

The model supplies reasoning. The harness gives it a workspace, tools, state, execution, and feedback.

Model

Produces and interprets language. Its outputs are probabilistic.

Coding harness

Codex or Claude Code lets the model read files, run commands, edit code, and observe results.

Our app

A Gradio chat that retrieves course slides and calls a model. It is the product being built.

Project context · 03 / 15

The repository gives the agent its working rules

Before a skill runs, the coding agent needs to know this project’s conventions, commands, and boundaries.

AGENTS.md

Repository instructions that Codex reads along the path to the current directory. Put durable project rules here.

CLAUDE.md

Claude Code’s project guidance file. Claude Code can also read AGENTS.md, so teams can share repository rules across harnesses.

Other useful files

Compound Engineering · 05 / 15

Six steps, one feedback loop

  1. BrainstormDefine the user task and boundaries.
  2. PlanChoose an approach and decide how to check it.
  3. WorkBuild the smallest useful implementation.
  4. SimplifyRemove avoidable complexity.
  5. ReviewTest the result against the task and risks.
  6. CompoundKeep a verified lesson for the next run.

Ask: Where have we made a decision that later steps should preserve? Where can a test or review catch a model’s plausible but wrong output?

Step 1 · 09 / 15

Brainstorm: decide what to build

Gather requirements: user, task, scope, boundaries, and success criteria. Leave implementation sequencing for planning.

In this demo

Who asks questions? Which course slides count as sources? What should the app do when the source material does not answer?

Different paths

A small, clear request may end with a short chat brief. Ambiguous software work gets a durable requirements artifact. Non-software work follows its own brainstorm route.

Handoff

The agreed requirements become the input to ce-plan. No code is written here.

While it runs: Listen for questions about product behavior, not library choice or implementation order.

Step 2 · 10 / 15

Plan: decide how to build it

Sequence the work, resolve technical choices, and decide how each part will be checked while preserving the brainstorm’s requirements.

Order

Read the slide corpus, retrieve relevant sections, compose a grounded answer, then add a Gradio conversation and checks.

Optimize the approach

Use existing repository patterns and the simplest viable retrieval design. Avoid adding a database or fine-tuning before evidence shows a need.

Verification

Specify supported, follow-up, and unsupported questions before implementation so the result can be judged.

While it runs: Watch the agent choose dependencies and checks. This is where cost, latency, and complexity tradeoffs are considered.

Step 3 · 11 / 15

Work: implement and verify

ce-work is an execution workflow. It carries the agreed plan through code changes and local verification, rather than stopping at plausible generated code.

Take in the plan

Check scope, existing code, workspace state, and the units of work before editing.

Build in steps

Implement the required behavior, integrate the parts, and keep the plan’s constraints in view.

Show evidence

Run meaningful checks, inspect failures, and complete the in-scope work. The standalone route also enters simplification and code review before shipping.

While it runs: Ask what the harness observed after each edit. A model’s first answer is a proposal; tool output and tests provide feedback.

Step 4 · 12 / 15

Simplify: make the code maintainable

Keep behavior, reduce the effort needed to understand and change the implementation. Fewer lines alone are not the goal.

Inspect

Look for duplicated logic, unnecessary layers, unused code, avoidable work, and tests or comments that add no value.

Change carefully

Prefer clear, explicit code. Preserve outputs, errors, ordering, safety checks, and tests that prove the feature works.

Verify again

Run the relevant checks after edits. If behavior preservation cannot be established, leave the change out.

While it runs: Can we explain the retrieval path in a minute? Does each helper earn its place?

Step 5 · 13 / 15

Review: challenge both plan and code

Document review

Read the requirements or plan; check coherence, feasibility, missing decisions, and risks; verify findings against the agreed goal; correct authorized issues.

Code review

Inspect the changed code and its intent; select risk-specific lenses; check correctness, regressions, tests, and project standards; report supported findings.

Adversarial pass

For substantial or risky work, try to break the assumptions. A configured second model can provide an independent pass; its findings still need verification.

While it runs: Ask for a question the app should decline. Check whether a displayed citation supports the answer, not just whether one appears.

Step 6 · 14 / 15

Compound: reflect and keep the lesson

After a verified problem is solved, ask what future work would benefit from remembering it.

Find the actual lesson

What belief proved wrong? What failure or review finding changed the implementation?

Choose a durable form

Keep it where it prevents a repeat: a test, lint rule, coding standard, or concise repository learning in documentation.

Feed the next loop

Future brainstorms and plans can reuse the evidence. If the outcome was routine and already clear from the code, there may be nothing to record.

While it runs: A failed unsupported-question check might become a regression test. Record the reason only if the code and test would not make it clear.

Wrap-up · 15 / 15

Inspect the answer, then improve the system

A working UI is a start. Ask whether the answer is supported, whether retrieval found the right passage, and what the next evaluation should test.

  • What did the coding harness do that a bare model could not?
  • Which part belongs to the skill, and which part belongs to the app?
  • Which course question would reveal a failure in retrieval or grounding?

Takeaway: The same engineering loop applies whether an agent writes the code or a team does. Good context, observable tests, review, and recorded learning make the next iteration better.
